# Skill and tool selection

Use the selected Matt Pocock skills as the primary engineering methods. Load
specialists when their subject matters. Resolve upstream skill references such
as `research` or `codebase-design` to their installed `mattpocock-` names. Read
support files relative to that skill's directory. A tool literally named Skill
is not required. If a referenced workflow is absent, use the available tools
and report the limitation rather than pretending it ran.

Keep explicit-only skills explicit, including pstack-unslop, interview wrappers,
setup and routing utilities. Use Unslop to edit prose after checking its facts;
preserve quotations, identifiers and domain terminology. Ordinary implementation
can proceed from an agreed request without an interview or a new issue.

Honor the user's existing authorization and agreed test interfaces. Apply the
repository's acceptance checks proportionately. For a working-tree review,
include staged and unstaged patches and new files; HEAD comparisons alone cover
only committed work. Use one primary general review method and add specialist
review for a distinct uncertainty. Report standards and requirements separately.

Use native tools and existing connections before adding overlapping MCP servers.
In T3, follow its tool routing, delegation, isolation, browser, PR and lifecycle
instructions. In a standalone client, use the tools actually available there.
Share requirements and evidence across clients; their hooks, permissions, agent
configuration and invocation controls are specific to each harness.

Delegate only within current authorization. Keep one integration owner, assign
independent outputs, and preserve task-owned checkouts and resources. The
optional engineering-workflow skill can support handoffs and resumption where
installed; it grants no additional permissions. Use repository coordination
guidance as the authority for task briefs, immutable inputs and queued jobs.
Record exact checks and source identity. Reuse evidence under that contract;
queue admission and a worker's success message do not establish acceptance.
