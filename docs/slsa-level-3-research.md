# SLSA level 3 research for nix-forge

Reviewed: 2026-09-14. Scope: the eight public, non-fork repositories in [nix-forge](https://github.com/nix-forge), their default `main` branches, public release records, and GitHub's current SLSA and attestation documentation. This note answers whether "SALSA level 3" is a standard, what the repositories currently prove, and what an implementation should claim.

## Answer

"SALSA level 3" is almost certainly a mistaken spelling of **SLSA Build Level 3**, not another supply-chain standard. SLSA 1.2 has separate Build and Source tracks. Build L3 means a hardened hosted builder that prevents one run from influencing another and keeps provenance-signing material away from user-defined build steps. Source L3 is a different claim about source-control technical controls and source provenance. [The SLSA 1.2 specification](https://slsa.dev/spec/v1.2/) makes that split explicit, and [the Build track](https://slsa.dev/spec/v1.2/build-track-basics) defines L3.

GitHub artifact attestations alone are **Build L2**, according to [GitHub's artifact-attestation documentation](https://docs.github.com/en/actions/concepts/security/artifact-attestations). GitHub documents a feasible route to Build L3: put the build and attestation in a reusable workflow, then have each release workflow call it. Both caller and reusable workflow need `contents: read`, `id-token: write`, and `attestations: write`; containers also need `packages: write`. [GitHub's L3 guide](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/increase-security-rating) says the reusable workflow itself must build and attest the artifact.

That is the recommended direction for released executables and archives. It is not a basis for claiming that all eight repositories, all Nix outputs, or their source revisions already meet SLSA L3.

## Current repository evidence

The following observations were made from the public `main` trees and public Releases API on 2026-09-14. "No release workflow" means no tag-release or release-asset workflow was found, not that the repository has no CI builds.

All eight repositories expose repository-level Actions settings with default workflow token permission `read`; seven require full-SHA action pinning, while `nix-homelab` did not on the review date. The current workflows visibly pin the actions used in release paths to full commit SHAs. GitHub says a full-length SHA is the immutable way to reference an action and supports an organization or repository policy requiring it. [GitHub's secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use) documents both points.

The inspection could read repository-level settings but GitHub denied the authenticated client access to organization-level Actions policy and default-permission endpoints. Repository ruleset inspection did not yield usable public rule details. Consequently, this research does **not** establish branch protection, tag protection, required reviews, environment reviewers, organization action allowlists, or a restrictive organization default token as facts. These are evidence gaps, not evidence that controls are absent.

## What can reach which level

### Released binaries and release archives

`nix-seal` can feasibly make a bounded **SLSA Build L3** claim for each released platform executable, and `ci` and `nix-config-framework` can make the same claim for their explicitly released source archives, once the reusable builder is deployed and verification is required. GitHub states that its normal artifact attestations provide Build L2 and that reusable workflows can isolate the build process to meet Build L3. [GitHub's level statement](https://docs.github.com/en/actions/concepts/security/artifact-attestations#slsa-levels-for-artifact-attestations) is the relevant platform claim.

That claim applies to the named artifact digest and the documented trusted builder. It does not prove that the artifact is safe, reproducible byte-for-byte, free of compromised dependencies, or suitable for another operating system. GitHub specifically warns that an attestation links an artifact to source and build instructions, while consumers must define and evaluate their own policy. [Artifact-attestation guidance](https://docs.github.com/en/actions/concepts/security/artifact-attestations) supports that limit.

Nix makes the proposed release build more repeatable than an unlocked build, but it does not turn a flake into SLSA L3 by itself. A `flake.lock` fixes input specifications and records input NAR hashes; the Nix manual says these locked values are the values supplied to flake outputs. [Nix flake reference](https://releases.nixos.org/nix/nix-2.26.0/manual/command-ref/new-cli/nix3-flake.html) describes this. A release manifest should record the commit, tag, target system, package attribute, `flake.lock` digest, resulting binary SHA-256, and optionally the output NAR hash. Consumers can then compare their locally built output to the released digest, but matching has to be demonstrated for each declared platform before calling it reproducible.

For `nix-seal`, Cargo metadata belongs inside the Nix input graph and SBOM, not in an unsupported claim that Cargo alone proves provenance. Cargo's lock file pins dependency versions for builds, while `cargo package` itself says its VCS snapshot is best effort and does not verify the package's provenance. [Cargo FAQ](https://doc.rust-lang.org/cargo/faq.html#why-have-cargolock-in-version-control) and [`cargo package`](https://doc.rust-lang.org/cargo/commands/cargo-package.html) establish those limits.

### Source and Nix flake repositories

The source-only repositories can publish precise source revisions and locked dependency graphs today, but they cannot honestly claim **SLSA Build L3 for "the flake"** without defining and distributing a particular built subject. A Git commit, `flake.nix`, and `flake.lock` are source inputs, not an executable or archive generated by the hardened builder. Attesting frequent test artifacts would also be the wrong target: GitHub advises signing software people will consume, rather than routine CI outputs or individual source files. [GitHub's attestation guidance](https://docs.github.com/en/actions/concepts/security/artifact-attestations#when-to-generate-attestations) says so.

They also cannot yet claim **SLSA Source L3**. Source L3 needs the source-control system to enforce the organization's technical controls for named references. Source L2 already requires continuous immutable history and source provenance for each new source revision. The SLSA Source specification calls for Source Provenance or a Source Verification Summary Attestation to communicate that evidence. [SLSA Source requirements](https://slsa.dev/spec/v1.2/source-requirements) define these requirements. GitHub artifact attestations are build provenance, not source provenance. No source provenance/VSA producer, public source-level policy, or independently inspectable evidence that GitHub rulesets enforce the claimed controls was found in this review.

## Recommended implementation

Build one reviewed, organization-owned reusable workflow in `nix-forge/ci`, pinned by callers to a full commit SHA. It should accept a deliberately small input set: caller repository/ref, Nix target system, a fixed package or archive recipe identifier, expected artifact names, and whether to produce an SBOM. It should:

1. Check out the caller's immutable tag commit with credentials disabled, set up the pinned Nix environment, and build the declared flake output or source archive.
2. Create a release manifest and SHA-256 files from the exact staged bytes. For Nix outputs, include the locked-input and output identifiers described above. For `nix-seal`, generate a CycloneDX SBOM per staged executable.
3. Invoke GitHub's attestation action in the reusable build workflow, immediately after staging, for every distributable binary/archive, checksum manifest, and SBOM. GitHub's official action produces SLSA build provenance by default and requires OIDC plus attestation write access. [The `actions/attest` repository](https://github.com/actions/attest) documents this behavior and permission model.
4. Upload those same staged files for a minimal caller publication job. The caller may use the protected `release` environment and `contents: write` only to create the GitHub Release. It must not rebuild, rename, replace, or generate new distributable bytes.
5. Document verification with `gh attestation verify FILE -R nix-forge/REPOSITORY` and require the expected reusable workflow using `--signer-workflow`. GitHub documents both normal verification and signer-workflow pinning. [GitHub's L3 verification guide](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/increase-security-rating) is the source.

Keep the builders on GitHub-hosted runners. Do not give the reusable build job release credentials, arbitrary long-lived secrets, or a self-hosted runner unless its isolation is separately assessed. Keep environment approval and `contents: write` in the publication job. A tag-triggered release also needs protected tag rules or an equivalent authorized-release process. Otherwise a principal who can create a matching tag can select the source revision that enters the builder.

At organization scope, enable restricted default `GITHUB_TOKEN` permissions, require full-SHA pinning everywhere including `nix-homelab`, allow only reviewed actions and reusable workflows, and apply rulesets to `main` and release tags. Require pull requests, current successful checks, no broad bypass, and two-party review where the organization intends to make a source-level claim. GitHub rulesets can require pull requests, reviews, status checks, signed commits, and block force pushes. [GitHub's ruleset reference](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) describes those controls. GitHub's new organization Actions policies can limit workflow events and actors, but they are public preview and should not be the only control. [Actions policies documentation](https://docs.github.com/en/organizations/managing-organization-settings/actions-policies/about-actions-policies) records that status.

Enable immutable releases for repositories that publish release assets. GitHub says immutable releases lock the associated tag and assets and add a release attestation; it recommends creating a draft, adding assets, then publishing. [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) documents this. This complements, rather than replaces, the build attestation.

Do not adopt `slsa-framework/slsa-github-generator` for new work. Its own README says it is no longer actively maintained and recommends GitHub artifact attestations instead. [Generator status](https://github.com/slsa-framework/slsa-github-generator) is decisive here.

## Validation and remaining evidence

This was a read-only review. I enumerated public repositories and workflow trees through the GitHub API, read local clones for `nix-conf`, `nix-homelab`, `nixpkgs-personal`, `nix-seal`, and `nix-config-framework`, inspected release metadata, and checked repository Actions settings. No build, release, or attestation verification was run. The next implementation should verify an actual release asset with the exact signer workflow, inspect the resulting provenance predicate and subjects, and run a clean rebuild comparison for every supported `nix-seal` platform.

Missing evidence before any public L3 statement includes: the organization and repository ruleset exports; protected-tag configuration; release-environment reviewer and deployment policy; organization Actions allowlist/defaults; the reusable workflow's final SHA and review history; an attestation retrieved for each release asset; an agreed consumer verification policy; and clean, independent Nix rebuild comparisons. GitHub notes that public-repository attestations are stored with GitHub and recorded in Sigstore's public transparency log, but attestations can also be deleted, so release evidence should be retained and continuously verified. [GitHub attestation storage](https://docs.github.com/en/actions/concepts/security/artifact-attestations) and [attestation lifecycle](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/manage-attestations) describe those facts.
