# Moonfin Linux desktop smoothness

Reviewed: 2026-09-28. Scope: Moonfin 2.6.0 source build, Flutter 3.47.4 Linux and macOS embedders, native Wayland on a high-refresh 4K display. Decision: which package or application changes could improve scrolling and navigation without introducing fragile engine patches.

## Answer

The established platform difference explains why 60 FPS alone does not guarantee equal smoothness. Flutter 3.47.4 on macOS uses a display-link callback with target presentation timestamps. Its Linux embedder does not provide a `vsync_callback`, so the engine uses a fixed 60 Hz fallback timer that is not phase-locked to the display. The Linux GTK renderer also schedules a GTK widget redraw after every Flutter frame. On the observed 150% Wayland output, GTK3 receives an integer 2× scale and this renderer sizes its buffer with that integer. The resulting buffer has about 1.78 times as many pixels as the visible area. These mechanisms can cause uneven presentation or extra work even when the app's own frame production stays below 16.7 ms, though their separate contributions to Moonfin's observed lag remain unmeasured. Moonfin also enables autoplay trailer previews on Home by default; a running preview was observed consuming roughly one CPU core. Compiling the native Linux desktop app with WebAssembly would not supply a different native compositor scheduler. The Flutter web client can use WebAssembly in a browser, but that is a different application target.

The current upstream high-refresh proposal is still under review. It includes changes absent from Flutter 3.47.4, and a Flutter maintainer specifically requested separation of the Wayland subsurface optimization because of possible side effects. There is no safe, small Moonfin package flag that enables correct compositor-paced 240 Hz output in the installed engine. An engine update or backport needs an isolated build plus measured frame-presentation and window-lifecycle tests.

## Findings and sources

1. **Frame scheduling.** The [Flutter 3.47.4 fallback source](https://github.com/flutter/flutter/blob/3.47.4/engine/src/flutter/shell/common/vsync_waiter_fallback.cc#L34-L42) uses a fixed 60 Hz interval. The [Flutter Linux tracking issue](https://github.com/flutter/flutter/issues/191245) states that the Linux embedder has no `FlutterProjectArgs.vsync_callback` and that display refresh metadata does not phase-lock rendering. This establishes an upstream limit; the share of the user's observed lag attributable to it has not been measured.
   The [macOS VSync waiter](https://github.com/flutter/flutter/blob/3.47.4/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterVSyncWaiter.mm#L67-L93) instead receives display-link callbacks with target timestamps, backed by the [macOS display-link manager](https://github.com/flutter/flutter/blob/3.47.4/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterDisplayLink.mm#L105-L161). The Linux launch log confirmed Flutter Impeller on OpenGL ES with the NVIDIA renderer. The macOS Flutter path uses Metal. This is a platform-path comparison, not a measured frame-time comparison between the two machines.
2. **Presentation path.** In [Flutter 3.47.4's GTK renderer](https://github.com/flutter/flutter/blob/3.47.4/engine/src/flutter/shell/platform/linux/fl_view_renderer.cc#L44-L80), each presented frame schedules `redraw_cb`, which calls `gtk_widget_queue_draw`. The [current tracking issue](https://github.com/flutter/flutter/issues/191245) describes the later Wayland child-subsurface renderer and its remaining GTK parent redraw. That newer renderer is absent from the installed 3.47.4 tree, so its experimental direct-commit patch cannot be cherry-picked as a narrow package fix.
3. **Fractional scaling.** [GTK3's scale factor API](https://docs.gtk.org/gdk3/method.Monitor.get_scale_factor.html) returns an integer. [Flutter 3.47.4's GTK renderer](https://github.com/flutter/flutter/blob/3.47.4/engine/src/flutter/shell/platform/linux/fl_view_renderer.cc#L55-L69) multiplies its widget allocation by `gtk_widget_get_scale_factor`. On the observed 150% Wayland output, a direct `wl_output` probe reported scale 2. Thus the renderer requests 2×2 = 4 pixels per logical unit where the screen displays 1.5×1.5 = 2.25, a 4/2.25 = 1.78 pixel-count ratio. This is a source-and-protocol inference, not a measured GPU-time breakdown. Forcing `GDK_SCALE=1` could reduce render work at the cost of compositor upscaling and possible blur; it needs a visible A/B before any package change.
4. **Status and evidence for proposed fix.** [Flutter PR #192342](https://github.com/flutter/flutter/pull/192342) adds a display-rate timer and changes Wayland parent commits. Its author reports 25–30 ms of GTK repaint work per frame at 4K/144 Hz on one KDE/AMD machine, but this is not a measurement of Moonfin on this NVIDIA machine. The PR is open; on 2026-09-22 a Flutter maintainer asked to split out the subsurface change because of possible side effects. The [tracking issue](https://github.com/flutter/flutter/issues/191245) further identifies missing compositor presentation timestamps, mixed-refresh tracking, and X11-specific behavior. A timer based on reported display refresh would not prove smooth physical presentation.
5. **Renderer choice.** [Flutter's Impeller documentation](https://docs.flutter.dev/perf/impeller) says Impeller is the Linux default in 3.47 and documents an application-level opt-out for diagnosis. A controlled local Skia build was previously tried without a clear improvement in an automated scroll capture, so making Skia the package default lacks evidence. Flutter also tracks an [NVIDIA/Wayland resize crash](https://github.com/flutter/flutter/issues/191775), but a crash report does not establish the cause of steady-state navigation lag here.
6. **Moonfin work during navigation.** The [trailer preview preference](https://github.com/Moonfin-Client/Moonfin-Core/blob/b86bbe6021eff5befdf311134bf3e831c032f21f/lib/preference/user_preferences.dart#L2479-L2482) defaults to enabled. The [Linux hardware-decoding preference](https://github.com/Moonfin-Client/Moonfin-Core/blob/b86bbe6021eff5befdf311134bf3e831c032f21f/lib/preference/user_preferences.dart#L2116-L2119) defaults to disabled, and the [trailer player](https://github.com/Moonfin-Client/Moonfin-Core/blob/b86bbe6021eff5befdf311134bf3e831c032f21f/lib/ui/widgets/media_bar.dart#L1568-L1578) consequently requests `hwdec=no`. A visible trailer preview coincided with roughly 85–90% of one CPU core and active GPU use in the observed session. Disabling Trailer Preview through the application's Personalization > Local Previews setting persisted after restart. This removes optional continuous media work while browsing Home, but it does not raise Flutter's frame cap. Hardware decoding was briefly enabled for evaluation; it selected `auto-safe` but did not substantially reduce preview CPU use, so the preference was restored to its original default.

   In the pinned [Moonfin Home implementation](https://github.com/Moonfin-Client/Moonfin-Core/blob/b86bbe6021eff5befdf311134bf3e831c032f21f/lib/ui/screens/home/home_screen.dart#L380-L415), a selected item debounces background updates, and the [backdrop builder](https://github.com/Moonfin-Client/Moonfin-Core/blob/b86bbe6021eff5befdf311134bf3e831c032f21f/lib/ui/screens/home/home_screen.dart#L669-L697) uses an image blur when enabled. Poster image decoding is already bounded for scrolling; [Moonfin issue #875](https://github.com/Moonfin-Client/Moonfin-Core/issues/875) documents that intentional quality/performance tradeoff. An isolated blur-off run did not reduce occasional raster spikes, so disabling the effect by default is not supported by these measurements.
   The app's [scroll-sensitivity binding](https://github.com/Moonfin-Client/Moonfin-Core/blob/b86bbe6021eff5befdf311134bf3e831c032f21f/lib/util/scroll_sensitivity_binding.dart) multiplies mouse-wheel distance while preserving the pointer event timestamp. It may change perceived wheel travel, but it does not alter the engine's frame pacing and cannot explain slow navigation transitions on its own.
7. **WASM scope.** [Flutter's WebAssembly guide](https://docs.flutter.dev/platform-integration/web/wasm) describes browser deployment of Flutter web. Native Linux Moonfin uses Flutter's Linux GTK embedder and native AOT output. WebAssembly does not make that native embedder use Wayland presentation feedback or the monitor's refresh cadence.
8. **Current runtime diagnostics.** A fresh native-Wayland launch on 2026-09-28 reported Impeller with hardware EGL. While Moonfin was visible and idle, eight one-second process-CPU samples were 17%, 0%, 0%, 0%, 0%, 1.9%, 0%, and 0% of one core; sustained CPU saturation is not evident at idle. Three uncaught D-Bus `ServiceUnknown` messages, one failed optional public-configuration request with HTTP 405, and GTK accessibility/cursor warnings occurred during startup; their counts did not rise during subsequent idle observation. A virtual mouse appeared in the gamepad list, but its device produced only three initialization events in five seconds. None of those log entries currently has evidence linking it to steady scrolling lag. Two prior Moonfin exits were recorded as SIGSEGV without retained core dumps; their cause and relationship to smoothness are unknown. A 60 Hz headless compositor output is also present, so future interactive measurements must verify that Moonfin is on the physical high-refresh output.
9. **Isolated Flutter frame timings.** A temporary source build added Flutter `SchedulerBinding.addTimingsCallback` telemetry. In a 2560×1440, 60 Hz headless Gamescope session with copied app state, the scale-2 Home run produced multiple 20-frame batches with build and raster p95 below the 16.7 ms frame budget, one batch with raster p95 36.2 ms, and cold-start build p95 73.3 ms. Repeating at GTK scale 1 gave a similar 33.7 ms raster spike. Repeating at scale 2 with Home backdrop blur set to zero gave raster spikes of 39.1 and 59.6 ms. These runs do not isolate a stable scale or blur improvement. The callback records app frame construction and rasterization, not the frame's physical presentation time. It also includes long gaps between Home's periodic animations, so the recorded inter-frame p95 cannot be interpreted as continuous scrolling FPS. Gamescope's headless compositor differs from the physical Hyprland session, and concurrent desktop activity prevented a valid live interaction trace. The timing results identify occasional app work but do not quantify the reported input lag.

## Validation and limits

This note inspected the pinned Moonfin package recipe and source revision, the installed Flutter 3.47.4 engine source, and first-party Flutter/Moonfin sources retrieved through 2026-09-28. The [upstream macOS release workflow](https://github.com/Moonfin-Client/Moonfin-Core/blob/b86bbe6021eff5befdf311134bf3e831c032f21f/.github/workflows/build.yml#L55-L59) pins Flutter 3.47.2, whereas the local Linux package uses 3.47.4; this small version difference alone has not been shown to cause the platform behavior. A direct Wayland protocol probe returned output scale 2 while the compositor configured 150% scale. A prior controlled local session confirmed native Wayland/NVIDIA rendering and low idle CPU, compared a temporary Skia variant, and observed uneven updates in synthetic scroll video; that video cannot isolate input generation, raster work, GTK repaint, or compositor presentation. The trailer preview setting was changed through Moonfin's UI, which synchronizes the preference, and its off state survived relaunch. Attempts to automate a settings-panel capture were invalid because concurrent desktop use changed the focused window or route; the private captures were deleted and no frame-rate comparison is claimed from them. The current launch logs and idle CPU samples establish the runtime path but do not measure scrolling. Three isolated, instrumented Home runs measured Flutter build/raster work, with scale and blur varied separately; their periodic animations are not a scrolling benchmark or a substitute for physical presentation timestamps. No engine patch or package edit was made. The PR author's timing was on different hardware and must not be extrapolated to this desktop.

## Implication for this repository

Keep the Moonfin source package on native Wayland and Impeller. Keep optional autoplay previews disabled when smooth browsing is preferred. A package-level refresh-rate override would hardcode a display assumption and leave GTK redraw overhead untouched. Measure a repeatable scroll/navigation sequence with engine frame timings and compositor presentation timestamps, then test one controlled variable at a time: backdrop effects, application scale, and a Flutter engine version with reviewed Linux presentation changes. Accept a packaged change only if it improves visible frame cadence and latency without regressing text clarity, startup, resize, maximize, playback, or output moves. Track Flutter #191245 and PR #192342; do not pin a private engine fork or change the global display refresh based on the current evidence.
