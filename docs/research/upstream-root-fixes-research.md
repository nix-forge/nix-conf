### Decision

Prioritize contributions which close gaps, then help existing PRs over their specific blockers. The largest avoidable duplication would be new PRs for Hyprshell modifier release/empty-special parsing, Stylix option renames, nom performance/unknown protocol types, Ghostty, nh, or the TypeScript dependency hash. Those already have active proposals or merged fixes. Full Hyprshell workspace identity, Hypridle inhibitor retries, nu_scripts completion syntax, nixf flake metadata, and nixos-anywhere effective SSH overrides have actionable gaps. Hyprland ancestry has a closed unmerged predecessor to acknowledge; rendering needs design review and broader regression evidence rather than shipping its large local diff unchanged.

None of the inspected maintainers supplied a reliable release ETA. An open release PR or a date generated in its changelog is not a promised release date. Merger alone does not retire a repair: the selected source/package must contain the fix and the specific unmodified acceptance test must pass.

### Details that change contribution priority

#### Hypridle: a safety-relevant follow-up rather than a new feature

The four-line local guard is narrowly aligned with `onIdled()` semantics: if an inhibitor arrives while a failed condition awaits retry, the retry must not fire the timeout except for listeners explicitly ignoring inhibitors. Current `main` preserves the bug. 193's earlier added follow-up clears pending retries across all listeners on user activity after an inhibitor toggle; that is a different case from a new inhibitor while the user remains idle. A useful upstream test deliberately fails the initial condition, adds an inhibitor, makes the condition true, checks no timeout while inhibited, and then checks allowed execution after release. Also cover `ignore_inhibit`, cancellation by activity, multiple rules, and no duplicate timeout.

[193 discussion](https://github.com/hyprwm/hypridle/pull/193#issuecomment-4679061425) documents the earlier orphaned-retry issue; [188](https://github.com/hyprwm/hypridle/issues/188) is motivation for condition support, not an inhibitor retry bug report. No exact matching follow-up appeared in `condition`/`retry` searches. Hypridle has GitHub Discussions disabled.

#### Hyprland: ancestry and rendering require separate contributions

The local lifetime patch is now broader than the old two-null-check proposal described in September research: it fixes `CSubsurface::size()` to use geometric size, changes ancestry traversal to the current ancestor, checks expired subsurface roles and color-description callers, and handles stale parent roles. Split independent geometry repair from lifetime/ancestry unless regression evidence establishes necessity. 15446 overlaps most ancestry changes and is neither rejected technical work nor an accepted fix: it is closed, unmerged, authored by deleted `ghost` account, with zero issue comments, reviews and review comments. Prior research observed deletion as closure cause; this fresh API check establishes no technical review, not its cause.

The rounding patch changes renderer pass composition, shaders, common masks, overflow, blur/dimming behavior and transformed passes. It cannot be justified merely as “disable subsurface rounding”: when children overlap parent corners, independent translucent masks can darken seams. 12554's [maintainer explanation](https://github.com/hyprwm/Hyprland/discussions/12554#discussioncomment-15176410) identifies inability to round just one corner as the prior constraint; local group composition is a proposed solution, not maintainer-approved architecture. 13320 has no accepted answer. 11590 is broader fractional/occlusion history; source comments are not proof its closure retires this patch. Newly inspected layer-shell discussions 16357/16398 concern missing subsurface tracking/damage, not this window rounding bug.

Current [hypr ecosystem AI policy](https://github.com/hyprwm/.github/blob/main/policies/AI_USAGE.md) permits local implementation/tests but forbids AI-written developer-facing submissions/descriptions; current policy also requires detailed disclosure and human understanding beyond supervised generation. Any future submission must follow that project's current rules and human contribution process. This task writes no upstream submission.

### Zen: existing native-builder issue and accepted caller-side precedent

The exact root-cause symptom already has [DeterminateSystems/nix-src421](https://github.com/DeterminateSystems/nix-src/issues/421), **open**, with a minimal `cp --no-preserve=mode` native-Linux-builder reproducer on macOS and a separate Caddy use case. Therefore do **not** recommend a duplicate new builder issue.

The [maintainer response](https://github.com/DeterminateSystems/nix-src/issues/421#issuecomment-4263522915) identifies Virtualization.framework/virtiofs limitations combined with cp's behavior, says there are no available Virtualization.framework knobs to fix it, and recommends fixing the caller sites using `--no-preserve=mode`. This is more specific than assuming a future Determinate release will resolve it.

The linked accepted [Crane964](https://github.com/ipetkov/crane/pull/964) explains that cp attempts to clear `system.posix_acl_access` through fsetxattr. Its previous preserve-xattr workaround was unsuitable for cp built without xattr support. The merged fix keeps `--no-preserve=ownership`, removes `--no-preserve=mode` and explicitly makes the copied output writable. That is a precedent for a narrow caller-side portability fix, not proof every cp flag deletion is equivalent.

Current [Nixpkgs Firefox wrapper](https://github.com/NixOS/nixpkgs/blob/89a0beb079b467d608c0b07069ef66812d33d634/pkgs/applications/networking/browsers/firefox/wrapper.nix) still contains:

```sh
cp -P --no-preserve=mode,ownership --remove-destination ...
chmod a+rwx ...
```

The local overlay applies only when browser.pname starts `zen-`; it replaces that full cp command string with `cp -P --remove-destination`. Its source assertion only checks command presence. The immediate chmod supports the hypothesis that writable executable mode can be preserved without cp's failing ACL-reset operation, but this pass does not prove all ACL/ownership/symlink/umask behavior is identical.

Recommended minimal new Nixpkgs proposal: edit the actual wrapper copy site, cite421/Crane964, preserve `-P`, replacement semantics and the intended ownership behavior, and explain explicit mode handling. Do not submit this repository's Zen-only `replaceStrings` overlay as upstream API design. A candidate retaining `--no-preserve=ownership` is closer to accepted Crane precedent than blindly dropping both flags; choose based on actual tests and desired wrapper semantics.

Before sending, run a minimal reproducer on affected native builder and ordinary Linux, inspect syscall failure if needed, cover existing destination/source symlinks and readonly executable source, verify final executable mode and ownership/ACL expectations, then build the affected wrapper/Zen. Broader Firefox caller support needs its own representative acceptance. This is conditional contribution work, not a tested patch recommendation. Retirement gate is the selected wrapper executing unmodified on the configured native builder with actual Zen acceptance; source merge alone is insufficient.

### Home Manager: propose a generic exclusion boundary, keep transaction policy separate

Current [copyApps module](https://github.com/nix-community/home-manager/blob/640725978b99076e18e069f6e7d2959124584f8f/modules/targets/darwin/copyapps.nix) exposes only `enable`, `enableChecks` and `directory`. It builds an Applications environment from `home.packages` and rsyncs it with checksum, permission/link handling, `--delete` and writable-mode flags. There is no source-exposed per-bundle exclusion option.

Merged [Home Manager9099](https://github.com/nix-community/home-manager/pull/9099) repairs a separate macOS26.3 signature-cache problem by not copying Nix-store mtime1. It does **not** provide excluded ownership domains, running-app detection, whole-bundle atomic replacement or rollback. Likewise copyApps initialization8031 and linkApps migration9085 do not establish those features.

The local override injects rsync exclusions derived from custom `config.macos.applications.protectedBundles`. That value is calculated from the local protected-app lifecycle configuration, including previous bundle names. This root-specific namespace and its transaction implementation cannot be copied into Home Manager unchanged.

A small generic upstream feature is plausible: for example an empty-default `targets.darwin.copyApps.exclude`/`excludedApplications` list with a documented contract for top-level app bundle names, preserving compatibility. The exact option name/shape should follow maintainer review. It should let an independent application manager opt out of copyApps without forcing all other apps out of normal Home Manager ownership. Keep the local adapter from protectedBundles to that generic list. This single feature could retire the textual module replacement while the independently verified local transaction manager remains intentional integration.

The generic API must define **both update and deletion** semantics. Existing excluded bundles should survive rsync `--delete` even when absent from the source; nonexcluded bundles should still update and obsolete nonexcluded apps should still disappear. Shell escaping alone does not make rsync wildcard syntax literal. Include explicit handling/tests for spaces, Unicode, glob characters or a deliberately documented validated pattern API, top-level anchoring and duplicates. Defaults must reproduce current behavior and first activation/linkApps migration must remain valid.

Additional source detail: `checkAppManagementPermission` currently calls `touch "$appBundle/.DS_Store"` for every existing bundle. The local patch changes only rsync flags, so it does not establish that protected bundles are excluded from every activation-time touch. If the new upstream API promises independently managed apps remain untouched, its permission-check loop should honor the same ownership exclusion or explicitly narrow its documented contract. Do not claim the current local exclusion implements a complete mutation barrier.

Running-app-aware atomic copy, signature/entitlement verification, quit consent, historical bundle retirement and rollback are a larger design change. Open a design discussion/proposal only after maintainer agreement and native macOS reproduction; do not bundle the entire local transaction engine into the simple exclusion PR. A user choosing excluded ownership is separable from everyone adopting that lifecycle policy.

Existing9099 body/current source were inspected. This is a documented current source/API gap plus bounded negative issue search, not proof no discussion exists elsewhere. No native rsync/signature/lifecycle tests were run in this review.
