# Desktop Ethernet and Wi-Fi networking

Reviewed: 2026-10-01. Scope: the desktop's systemd-networkd uplinks and private homelab listeners. Upstream behavior was checked against current systemd, Linux kernel, and NixOS documentation. The validation below records the subsequent activation and client checks.

## Answer

Prefer Ethernet for ordinary traffic. Keep Wi-Fi configured as an optional fallback if the desktop should remain reachable when the cable, switch port, or Ethernet adapter fails. Keeping it active costs a second association and DHCP lease, and gives the host two addresses on the same subnet. If that fallback has no value, disconnecting Wi-Fi is simpler and removes one radio connection and one reachable address. Neither choice alone moves a service that binds a specific IP address.

For this repository, the homelab address, listener, private DNS record, and readiness condition must agree. A lower Ethernet route metric does not make a listener bound to the Wi-Fi address answer on Ethernet's address. A service waiting for `wlan0` also remains unavailable if Ethernet works but Wi-Fi does not.

## Findings and sources

- systemd-networkd manages links matched by `.network` files. `RouteMetric=` in the DHCPv4 and IPv6 router advertisement sections sets route preference for those acquired routes. A smaller metric makes Ethernet the preferred route when comparable routes exist. This governs outgoing route choice, not which local address a server binds. [systemd.network source](https://github.com/systemd/systemd/blob/main/man/systemd.network.xml), [systemd-networkd source](https://github.com/systemd/systemd/blob/main/man/systemd-networkd.service.xml).
- `systemd-networkd-wait-online --interface=NAME:routable --ipv4` waits for a specified interface to have a routable IPv4 address. Repeating `--interface` with `--any` succeeds when one specified interface is online. A zero timeout disables its own timeout. A check for either interface proves only that one has an address; it does not prove that a particular configured listener address exists. [systemd-networkd-wait-online source](https://github.com/systemd/systemd/blob/main/man/systemd-networkd-wait-online.service.xml).
- systemd cautions against making server startup depend broadly on `network-online.target`; the target marks a past readiness point and cannot guarantee continuous connectivity. For a server that binds a concrete interface address, use a readiness condition that matches that address, or make the server handle address changes. [systemd network-online guidance](https://github.com/systemd/systemd/blob/main/docs/NETWORK_ONLINE.md).
- Linux treats IPv4 addresses as owned by the host, which can produce ARP replies on another interface when both links share a subnet. `arp_ignore=1` restricts replies to addresses assigned to the incoming interface; `arp_announce=2` selects a suitable outgoing-interface address for ARP announcements. `arp_filter=1` requires source-based routing to work as intended, so it is not a substitute for those settings in an ordinary two-link setup. [Linux IP sysctl documentation](https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html).
- NixOS exposes native `.network` settings through `systemd.network.networks`; its official wiki recommends that interface for networkd configurations. The repository already uses networkd for IP assignment and IWD for Wi-Fi association. Running another connection manager over the same physical links would introduce competing owners without solving the fixed-address service dependency. [NixOS systemd-networkd documentation](https://wiki.nixos.org/wiki/Systemd/networkd), [NixOS IWD documentation](https://wiki.nixos.org/wiki/Iwd).

## Repository observations and recommendation

The desktop has DHCPv4 and IPv6 router advertisements on both physical links, with Ethernet route metric 100 and Wi-Fi metric 600 in [`hardware/networking.nix`](../../hosts/nixos/desktop/local/hardware/networking.nix). Both links are excluded from the global online wait. ARP settings address the same-subnet case. A runtime route lookup on 2026-10-01 also selected Ethernet for outbound IPv4 traffic.

The shared network data in [`network.json`](../../hosts/shared/local/network.json) now selects the wired reservation. [`homelab/https.nix`](../../hosts/nixos/desktop/local/homelab/https.nix) uses that address for the private HTTPS listener and wildcard DNS update, and waits for `enp13s0` to receive routable IPv4. The same shared address also reaches the MacBook's SSH host entry, Sunshine's allowed origin, and the music listener. Wi-Fi remains associated for desktop SSH and outbound recovery when Ethernet fails. The homelab deliberately remains bound to Ethernet; failover of inbound services would require separate listener and DNS behavior.

DHCP reservations on the router should remain the source of IPv4 addresses; do not also assign those addresses statically in networkd. Confirm that the reservation belongs to the Ethernet adapter's actual client identity and that no second client has the address. Keep the existing private source filters on the firewall and reverse proxy when moving the listener. The address change is not permission to widen inbound access.

## Validation and limits

The runtime check established both DHCP leases and route preference before activation. Focused Nix evaluations returned the wired address for the HTTPS listener and the Ethernet readiness command. The full desktop build passed after the Actual host module selected its CLI from the personal package flake output. A dry activation passed, then the built generation was activated through the MacBook's root SSH key. The first live switch reported a failure because the DNS reconciliation guard found records for the old address. A read-only API preflight identified the expected DNS-only wildcard A record and one exact A record retained beside a CAA policy. Both A records were changed to the wired address through Cloudflare's [record update API](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/edit/) and verified before the reconciliation unit was rerun successfully.

After clearing the desktop's local DNS cache, both reviewed names resolved to the wired address. TLS-verified requests from the MacBook reached the Actual and Jellyfin HTTPS sites through ordinary DNS; both reverse proxies, networkd, SSH, and Blocky were active, with no failed systemd units. The MacBook also reached desktop SSH through the Wi-Fi address. A timed rollback was armed for activation and disarmed after these checks. Cable unplug and router failover behavior were not tested. The MacBook's active SSH alias still uses the Wi-Fi address because its older checkout has not received the shared network data; sync that checkout and activate its Home Manager configuration to move the alias to Ethernet.
