# Upstream contribution roadmap: personal packages

> Historical snapshot: personal package recipes referenced here have since been retired or renamed. These audit findings describe the cited source, not the current package selection.

Reviewed: 2026-10-16. Scope: **69 non-Craft recipes and 35 patch artifacts**, comprising the 68-recipe matrix below plus Aurral and its seven patches. See the [decision roadmap](upstream-contribution-roadmap-research.md). Package adoption and product-patch retirement are separate decisions.

## General package matrix: 68 recipes

Reviewed: 2026-10-16. Read-only working-tree snapshot; no builds, evaluations, source changes, upstream comments, issues or PRs were made. Scope: **68 non-Craft, non-Aurral package recipes and all 28 `.patch` artifacts beneath them**. Craft family and Aurral are assigned elsewhere. Recipe scripts, generated substitutions and wrappers also matter; absence of a `.patch` file does not establish stock-package parity.

### Decision

The best immediate contributions are finishing existing narrow PRs and supplying missing regression evidence. Opening replacement PRs for work already under review would increase maintenance. Some personal packages provide new upstream packaging; others deliberately change product behavior, distribution identity, assets or defaults. The latter do not disappear just because Nixpkgs packages the same application version.

Highest-value paths:

1. **Already upstream, wait for a release/pin:** Wardrowbe's Redis parser is merged in app PR #223 after the current 1.11.0 release. The1.12.0 release PR #260 is open/approved; no release date is established. Remove only Redis hunks after a published source contains the merge and URL/parser tests pass. Noctalia's tray-size fix is merged PR #4579 and already in5.3.0; prior audit retired it. Nixpkgs Noctalia5.3.0 update574528 and BookOrbit3.4.0 update573797 are merged. BookOrbit is a promising whole-package consolidation candidate, subject to sandbox/migrations/runtime parity.
2. **Existing exact upstream PRs:** Blueair logging49, VeSync credential files48, Soularr shared cleanup204, Wardrowbe OIDC225, Noctalia greeter141/142/144. Continue these; do not open duplicates. Their aggregate statuses do not cover every local hunk.
3. **New narrow bugfix PR candidates:** REA precompiled Darwin helper discovery, Hyprlock ordered graphics cleanup, Noctalia exact PipeWire application ID precedence and external wired default-route reporting, ReactFlux `.mts/.cts` parser configuration, Stirling engine writable state. These require focused upstream reproductions/tests before submission; search results were incomplete evidence, not proof no equivalent work exists.
4. **Feature scope first:** Wardrowbe planning/AI browser-account/model UI, Noctalia multi-endpoint media cards/workspace styling, Hyprlock authentication UI, and Jellyfin subtitle options/rendering. Existing discussions and partial PRs should establish accepted scope. Wardrowbe's maintainer explicitly requested Discussions before future large changes.
5. **Packaging contributions:** Existing submissions should be helped rather than duplicated (Claude Desktop537215, REA574658, Soularr524201/399031, LinearMouse277481, macOS Steam499915, Vorssaint574546). Other clean standalone recipes are potential Nixpkgs additions, but accepting a recipe removes only packaging duplication, not its patched behavior.
6. **Explicit permanent exceptions:** Keep `codex-latest` and `chatgpt-latest` independently updated, regardless of temporary stock parity, as the user requires. Their underlying builder fixes can still be upstreamed.

### How evidence was checked

Fresh authenticated GitHub GraphQL searches covered historical issues and PRs on exact symptoms and identifiers, package-title searches in Nixpkgs, specific contribution authors, and selected matching PR bodies/reviews/comments/unresolved review threads. Core REST requests fetched the 100 most recently updated issues/PRs for 13 patch-owning repositories. These bounded recent lists were supplemented by historical searches; they were not called complete issue inventories.

Discussions were checked separately. Noctalia shell and greeter, Blueair, VeSync, Samsung, ReactFlux and Nixpkgs report GitHub Discussions disabled. Wardrowbe has 8 discussions; all 8 were retrieved and relevant250/251/214 read. Soularr import discussions 202/179 were read. Focused discussion searches also covered REA/Nix, AudioMuse/ports, Jellyfin/subtitle appearance, Stirling/engine state, Hyprlock/pointer, Bitwarden/macOS, Anthropic/licensing, Scrypted/NixOS. These do not substitute for searching external forums or every historical discussion. Nixpkgs comments link relevant Discourse threads where present.

Nixpkgs master recursive tree, top-level all-packages/aliases and selected recipes were inspected to avoid exact-by-name false negatives. The global recursive tree is **truncated** (73,577 records), so this is not an evaluated proof that all other attrs are absent. Confirmed examples: LibreOffice has `libreoffice-bin`; T3 Code is `t3code`; AudioMuse's Navidrome plugin lives in `navidromePlugins.audiomuseai`. Negative searches below mean no matching submission found in the stated search, not universal absence. No ETA is inferred from approval, issue closure, or elapsed age.

Raw source/search/review captures: `personal-raw/`; inventory: `personal-inventory.json`. Prior retirement inventory is context only and has been superseded where fresh evidence disagrees.

- **VeSync `credential-files.patch`:** [PR #48](https://github.com/mickgiles/homebridge-tsvesync/pull/48) is OPEN, “Read VeSync credentials from runtime files,” with no comments/reviews. **Action: support existing PR.** Gate: release contains schema, runtime file reader and credential precedence/error handling; installed plugin tests verify file credentials, explicit values, missing/unreadable files, newline handling and no logging. Implementation follow-up: existing PR 48 now includes three resolved-file-username session regressions; native ARM64 macOS / Node 24 passed all 221 tests across 21 suites, build and lint. - **Samsung `strict-power-state.patch`:** This is a much larger experimental opt-in `PowerState.Strict` detector plus safe toggle guards, NOT just empty-string handling. [Issue702](https://github.com/tavicu/homebridge-samsung-tizen/issues/702) explains false-on in standby; [closed-unmerged PR #750](https://github.com/tavicu/homebridge-samsung-tizen/pull/750) proposed empty-string handling, but maintainer said v6 already evaluates empty values as off. Generic new PR now would be premature. Remaining local package can retire only after exact supported-model behavior is accepted and released.

### Main conclusion

Do not upstream the seven-patch stack as one PR and do not mechanically port it to main. **Two major changes have already landed after stable:** [1045](https://github.com/lklynet/aurral/pull/1045) replaces the entire limited ListenBrainz fallback design; [1132](https://github.com/lklynet/aurral/pull/1132) implements lossless native tagging, dedicated private identity tags and migration, overlapping most of the native-audio patch. [1063](https://github.com/lklynet/aurral/pull/1063) and [1067](https://github.com/lklynet/aurral/pull/1067) merge two narrower correctness fixes. These are release/pin blocked for the current stable package, not requests for duplicate contributions.

Residual source differences worth focused reproductions are (1) release-group IDs still being fed into the scanner's release-ID fallback, (2) persisted/enriched artist duplicates and startup repair, (3) late Lidarr exact-path metadata on unchanged files, and (4) compatibility of the local dedicated-tag format/partial identity updates with the new upstream writer/reader. Public-history/token alignment, higher-quality/canonical artwork and externally managed Navidrome libraries involve product decisions: propose a narrow feature or reproduce a precise correctness failure, rather than assert maintainer-approved bugfix status.

No patch is declared removable from the current 2.10.0 package based solely on this source review. A next stable source containing these merges should substantially reduce the stack, but it also changes architecture, Node/native dependencies and matcher requirements, so acceptance must be against the chosen release and actual upgraded library data.

### All seven local patches

#### 1. `lidarr-metadata.patch` — correctness candidates remain, but split them

Local behavior: exact normalized file-path join to Lidarr-provided MBIDs/images; preserve file-derived identity keys while enriching tags; revisit unchanged files when metadata appears; repair only known stored group-as-release contamination; six-hour reconciliation for missed events/outages.

Current [scanConfiguredLibrary](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/libraryIndexService.js) supplies Aurral job metadata for own-library scans, but its Lidarr `scanMusicRoots` call has no metadataEnricher/metadataLookup. [libraryFileScanner](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/libraryFileScanner.js) skips size/mtime-unchanged files **before** calling metadataEnricher. Its `applyMetadataEnrichment` still sets both `musicbrainz_albumid` and `musicbrainz_releasegroupid` from `trusted.albumMbid`. Current [systemTaskWorker](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/systemTaskWorker.js) `library-index-refresh` case still returns without scheduling work.

This supports narrow **new bugfix candidates**, not proof all broad scanner changes should ship. Sequence:

1. Reproduce scanner release/group confusion with embedded AURRAL_IDS and no real release tag; preserve valid release tags and existing row identity. Fix this active path instead of reviving old taggerPR1065 wholesale.
2. Reproduce missing exact-path Lidarr metadata in production scan with mocked API and real generated file. Ask whether upstream wants enrichment from Lidarr vs its newer generic fill-tags workflow. Existing [1132 tag-fill module](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/libraryFiles/tagFill.js) searches MusicBrainz, validates recording/release matches and fills actual empty audio fields; that is **not** the same authoritative Lidarr exact-path join.
3. Separate late-metadata refresh/no-op scheduling fix from routine 6h policy. A forced full-scan workaround is not equivalent to cheap metadata-only reconciliation, but blindly adding whole-library recurring load may not be acceptable.

Retirement gate: tagless file indexed first, metadata arrives without size/mtime change, exact path join fills IDs/art; original album/track favorites and keys remain; true releaseID separate from groupID; contaminated stored group-as-release repaired only when known; no overwriting real release; API failure followed by recovery, mapped paths and stale watcher events; tests preserve new performer/album-owner separation and Lidarr-off behavior. No live filesystem/provider reproduction was run here.

#### 2. `listenbrainz-discover.patch` — mostly replace with upstream architecture

Local stable-only fallback adds charts, recommendations, playlists/flows/previews and no-key UI. [1045](https://github.com/lklynet/aurral/pull/1045) explicitly deletes this fallback architecture, supplying similar artists via ListenBrainz labs, metadata batches, sitewide stats, MusicBrainz tags, Deezer toptracks and per-user discovery. **No PR to transplant the 1,600-line fallback patch.**

When stable includes1045, adapt package tests and configuration to its sharedpipeline. Only a reproducible missing user-facing capability should become a separate issue/feature proposal, e.g. a particular playlist source not preserved. Similarity/network source behavior is not bytewise equivalent to local curated lists, so compare requirements rather than patch application.

Retirement gate: no Last.fm key, separate users/profile history, recommendations/feedback modes, preview/flow generation, sitewide charts, provider timeout/429 recovery and request cancellation, Last.fm add/remove cache transition, authenticated/public history and no real submissions. Appropriate frontend production/browser checks needed. Stable2.10 still uses fallback, so retain until source release migration rather than port to current main.

#### 3. `listenbrainz-connect.patch` — merged client slices plus a residual connection feature

Local behavior: per-user Connect card/dialog, public history vs encrypted-token scrobbling, optional expected username validated before save, history profile aligned transactionally to validated token owner, fresh profile bootstrap status, client User-Agent and global 429 cooldown.

Current [api client](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/apiClients/listenbrainz.js) already has app/version User-Agent, request limiter, bounded retry/rate-limit wait for request flows, and correct1063 release-group submission. Do not submit those duplicates. Pacing differs (350 ms/current bounded retries vs local serialized1s/shared cooldown); compare real provider contract and tests, not identical intervals.

Current [scrobbling link route](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/routes/scrobbling.js) validates token, saves encrypted token+verified displayName and returns connected/displayName only. It does **not** consume expectedUsername or update user's public-history profile in that route. That is a residual **workflow/product consistency proposal**, not automatically a security defect: deliberately linking a different valid account may be legitimate unless UI promises alignment. Current bootstrap [health](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/routes/health.js) no longer exposes the same `listenbrainzConfigured` capability at all after 1045. Therefore don't port the old stale-bootstrap fix to a removed field. Retain response-redaction tests as an acceptance property, not claim main leaks tokens without evidence.

Minimal contribution: agree Connect-versus-Playback UI and whether history/scrobbling identities are independently editable; then expected-account guard/transactional alignment if desired, with screenshot and narrowly scopedroute tests. If only a present UI stale-state bug reproduces, contribute that isolated bugfix. Test token rejection/empty owner, mismatched expected owner preserving old settings, valid atomic save, per-user isolation, disconnect vs public-history semantics, token redaction and 429 across lookup/link/write; don't submit real listens.

#### 4. `native-audio-tags.patch` — substantial upstream implementation exists; upgrade compatibility needs evidence

[1132](https://github.com/lklynet/aurral/pull/1132) and current [audioTags.js](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/audioTags.js) already implement dedicated custom tags across Xiph/ID3/MP4, standard MusicBrainz fields, unrelated-tag preservation, atomic siblingcopy+rename, legacy grouping/comment/description migration and no ffmpeg remux. The replacement uses node-taglib-sharp instead of Mutagen. Upstream [audio tagtests](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/.tests/download/audio-tags.test.js) cover retained ratings/lyrics/ReplayGain/grouping/art, releaseID preservation, known-different-group releaseID clearing, hardlink isolation and refusing fragmentedMP4. This changes earlier assessment that dedicated tags require a new featurePR. **Do not propose a new native-tagging system or add Mutagen upstream just to match local choice.**

Important residual differences/upgrade gates:

- **Existing local native-tag payload format:** local `write_audio_tags.py` stores `AURRAL_IDS=`+JSON inside the dedicated tag. Current audioTags.parseIdentity accepts plain or prefixed JSON, but [downloadUtils.readAurralIdentity](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/downloadUtils.js) uses JSON.parse directly on dedicated native value. Scanner calls the latter. Local legacy grouping may already be cleared, so existing dedicated prefixed identities risk becoming unreadable to the scan path. **High-value compatibility regression/reader normalization PR candidate**, reproduce using actual local FLAC/MP3/MP4 output and helper/scanner path; avoid claiming runtime failure before executing.
- **Partial identity updates:** local writer merges existing dedicated identities with supplied nonemptyfields. Current writeAudioTags writes suppliedidentity object wholesale. Is isolated title/track update invoked with only oneidentity field in real production? Reproduce that call path before calling upstreambug; either merge intentionally or ensurecaller always supplies completeidentity. Current reader correctly overlays own fields overlegacy when both parse.
- **Explicit selected releaseID:** buildResolvedJobTrack carries releaseMbid, but writeAudioMetadata currently maps releaseGroupMbid and no releaseMbid into writer. Existing release remains unless a changedgroup clearsit; this is the **explicit1132 policy**, not old1065 selectededition behavior. Discuss exact albumgrab assignment requirement and Navidrome grouping before changing it. Don't restore groupID as standard releaseID, and don't assume every differing source edition is invalid.
- **Release policy difference:** local writer always keeps genuine existingrelease absent an explicit replacement. 1132 intentionally clears one when a changedreleasegroup provesit belongs elsewhere; upstreamtest enforcesit. Decide whether that upstreamcorrectnesspolicy satisfieslocalrequirements, or documentremainingintentionalvariant. Do not blindly portpreserve-all hunk.
- **Filesystemmetadata:** local wrapper restoresmode/owner aftercopy. Upstreamcopy+rename must be tested for intended file mode/owner/group/ACL behavior under actual service user/hardlinks, and safe cleanup onerrors; codeinspection alone doesn'tprove samecontract.

Retirement gate: next stable includes 1132 and correct native dependency/caller hooks; port local generated-audio regression inputs to renamed API; FLAC/MP3/MP4 encodedaudio hashes unchanged, unrelatedtag/art preservation, valid grouping preserved and only validlegacy markers removed, native over legacy precedence, prefixed and plain payload compatibility, partial identity operations, known/unknown/different-group releaseIDs, sourcepermissionandhardlink handling, fragmentedMP4 nochange/error and migration restart idempotence. Preserve existing upgradedlibrary identity rather than only testing new files. No new executable test was run here.

#### 5. `artist-identity.patch` — merged management fix, persisted duplicate repair remains

[698](https://github.com/lklynet/aurral/pull/698), [714](https://github.com/lklynet/aurral/pull/714) and [958](https://github.com/lklynet/aurral/pull/958) establish promotion, canonical metadata and manual MBID foundations; [1067](https://github.com/lklynet/aurral/pull/1067) fixes management transfer. Current [mergeLibraryArtistInto](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/libraryMediaStore.js) preserves stars, calendar, albums, ownership, monitor_rules and search timestamps, then invalidates/rebuilds search. **Do not port an older, simpler SQL transfer over this.**

The current fallback query still requires `mbid IS NULL`; a name-keyed row already enriched with the same MBID is excluded. No local-equivalent startup sweep of such persisted duplicates appears in inspected libraryMediaStore/appRuntime. Residual **bugfix candidate**: create a name-keyed row with populated MBID alongside its canonical MBID-keyed record, including management, stars and albums. Use 1067 as context, rather than submitting another management-transfer PR.

A minimal fix should reuse the current merge helper and respect current identity authority and performer handling. Separate persistent migration from browser cache-version policy; prove an existing Recently Added cache actually obscures repair before requesting a new cache key. Gate fresh promotion, enriched-name promotion, canonical-existing merge, startup idempotence, canonical management precedence, album/star/calendar/search references, no same-name/different-MBID merging, and preservation of newer monitor fields. [1143](https://github.com/lklynet/aurral/pull/1143) separates names in other scripts; normalization and fuzzy-name merging must preserve that.

#### 6. `canonical-artwork.patch` — selection/quality policy, not a ready-made bugfix

Local behavior prioritizes a release-group CAA front over provider edition images, rejects non-front images, versions old cache keys, raises 512px/quality 70 to 1200px/quality 90 and selects larger Deezer fallback images. Current [releaseGroupCoverService](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/releaseGroupCoverService.js) still uses `rg:` cache keys, accepts the first ranked image if no front exists, and queries its provider before CAA. [imageProxyService](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/imageProxyService.js) remains 512px/150KiB/quality 70. Merged [373](https://github.com/lklynet/aurral/pull/373), [467](https://github.com/lklynet/aurral/pull/467) and [753](https://github.com/lklynet/aurral/pull/753) overlap ranking, fallback and caching but do not implement equivalent canonical selection. Newly merged [1205](https://github.com/lklynet/aurral/pull/1205) handles authenticated artwork for unidentified albums, a different path whose protections must survive any port.

Minimal proposal: agree whether the UI represents a canonical album or an owned edition, then propose an optional quality profile with explicit bandwidth/disk limits. A reproducible wrong non-front image or stale-cache bug can be a separate fix. Local cache-version names need not become an upstream API. Gate release-group front versus edition selection, no-front/provider fallback,404/429/transient errors without poisoning cache, aspect ratio/no enlargement, cache migration, batch consistency and authenticated private artwork. Higher resolution is a product tradeoff, not proof of a defect.

#### 7. `navidrome-managed-library.patch` — optional least-privilege integration feature

The local opt-in mode uses a host-managed path, verifies playback music-folder access through Subsonic, skips administrative create/update/scan calls and invalidates the indexed-songs cache. Current [navidrome.js](https://github.com/lklynet/aurral/blob/e70f0ed5d4b0ffdf90c64ca810575afc31defca1/backend/services/navidrome.js) still calls startScan and getLibraries/updateLibrary/createLibrary in ensureAurralLibrary. An exact managed-Navidrome search found no equivalent feature PR. Optional destination 612 and playlist-protection work are different capabilities.

**New feature proposal requiring maintainer agreement:** externally owned library lifecycle, an ordinary playback account and explicit unavailable actions. Current private-playlist protection checks adminRole; skipping library administration must not promise visibility into private playlists or weaken that boundary. `getMusicFolders` proves a readable folder exists, not that the server's filesystem path matches the supplied host path. Deployment must supply correct mapping and permissions; a generic feature should explain that trust boundary.

Gate ordinary-account playback access, denied/no-folder failures, no library create/update/startScan calls, independent host rescans reflected after cache invalidation, unchanged original administrator mode, intact private-playlist ownership rules and configuration path mappings. Retire after a released configurable mode passes these checks; a Navidrome version change alone is insufficient.
