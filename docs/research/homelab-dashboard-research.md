# Research question

Reviewed: 2026-10-01. Scope: a private, polished landing page and HTTPS availability view for services on a NixOS homelab and a Raspberry Pi. Decision: retain and improve the existing Homepage plus Gatus stack, or replace it.

## Answer

Keep Homepage as the single navigation page and Gatus as the independent health monitor. The repository already generates both from one endpoint inventory. Homepage has service tiles, bookmarks, tabs, layout and theme options, and a Gatus summary widget. Gatus checks HTTP responses, certificate expiry, and other protocols on a schedule, with alerts and persistent history options. This pairing meets the stated need with less migration work and less duplicated state than replacing it with a new dashboard. [Homepage services](https://gethomepage.dev/configs/services/), [bookmarks](https://gethomepage.dev/configs/bookmarks/), [settings](https://gethomepage.dev/configs/settings/), [Gatus widget](https://gethomepage.dev/widgets/services/gatus/), [self-hosted Gatus README](https://github.com/TwiN/gatus/blob/master/README.md).

The first change should be a distinct browser URL for each service. The current dashboard uses `endpoint.url` as `href`, while many inventory entries set that URL to `http://127.0.0.1:<port>`. In a browser on another device, loopback means that device, and these links cannot serve as the requested HTTPS launchpad. Keep host-local `healthUrl` for Gatus and add a browser-facing HTTPS address for each published service. A separate field also makes exceptions explicit for APIs, local-only admin pages, and Pi services. [Current endpoint model](../../nix-homelab/modules/operations/default.nix), [Homepage service URL and site monitor distinction](https://gethomepage.dev/configs/services/).

The upstream release pages above give current project context, not the versions in this flake. The running desktop currently uses Homepage 2.3.0 and Gatus 5.36.0, as reported by their systemd `ExecStart` paths on 2026-10-01. The next build could select different versions because the working tree includes a flake lock change. Check the evaluated packages before relying on a new feature.

Gatus supports HTTP, ICMP, TCP, DNS, response-body and response-time conditions, certificate expiration, alerts, and Prometheus metrics. Its default concurrency is three and its default HTTP timeout is ten seconds. Those defaults can delay checks if many slow endpoints are added; short timeouts and considered intervals matter more than a very fast poll cadence. Gatus defaults to in-memory history and supports SQLite or PostgreSQL persistence with bounded result counts. [Gatus self-hosted configuration](https://github.com/TwiN/gatus/blob/master/README.md#configuration), [storage](https://github.com/TwiN/gatus/blob/master/README.md#storage), [recommended interval](https://github.com/TwiN/gatus/blob/master/README.md#recommended-interval).

Monitor both the internal app health endpoint and, where valuable, its browser-facing HTTPS URL. An internal 200 proves only that the process or backend responds. A separate HTTPS check from a suitable network position tests DNS, the proxy, TLS, and authentication redirects. Gatus has a `[CERTIFICATE_EXPIRATION]` condition for HTTPS checks. Do not treat a 302 to login as proof that the authenticated application works. This is an inference from the different paths each probe traverses. [Gatus example configuration](https://github.com/TwiN/gatus/blob/master/config.yaml), [Homepage site monitor behavior](https://gethomepage.dev/configs/services/).

For security, keep Homepage and Gatus listening on loopback. The desktop now declares a private nginx HTTPS route for Homepage, uses its built-in password gate with a dedicated sealed credential, and limits login attempts in nginx. Gatus remains loopback-only. Homepage recommends a reverse proxy or VPN even with v2 authentication. Set `HOMEPAGE_ALLOWED_HOSTS` to the exact dashboard host, never `*`; Homepage has no application-level password rate limit. Keep widget API secrets in runtime credentials, avoid Docker socket access unless there is a concrete need, and avoid action widgets until their permission boundaries are specified. [Homepage security and authentication](https://gethomepage.dev/installation/), [Docker socket proxy advice](https://gethomepage.dev/configs/docker/), [Gatus self-hosted security options](https://github.com/TwiN/gatus/blob/master/README.md#security), [desktop dashboard](../../hosts/nixos/desktop/local/homelab/dashboard.nix).

For resource use, keep the always-on monitor on the main homelab host and represent the Pi with network probes and HTTPS tiles. Do not add a second monitor on the Pi merely to list Pi services. Homepage's `siteMonitor` checks are useful for a visual hint, but enabling them for every tile duplicates Gatus traffic. Gatus's bounded result storage and modest probe intervals permit a small local database if history across restarts is wanted. No project-wide CPU, RAM, or page-load benchmark was performed, so this is a configuration judgment rather than a measured ranking. [Homepage monitor behavior](https://gethomepage.dev/configs/services/), [Gatus storage and concurrency](https://github.com/TwiN/gatus/blob/master/README.md#configuration).

## Validation and limits

Before activation, the desktop's nginx configuration had no dashboard server name, and its Blocky rebinding allowlist had no dashboard name. The wildcard DNS record resolved on another LAN client, but nginx rejected the unknown TLS name; the desktop resolver dropped the private-address answer. These were separate effects of the unactivated configuration. The shared module now rejects HTTP 403 in browser-route probes because a client access denial would otherwise appear healthy. [nginx TLS name handling](https://nginx.org/en/docs/http/ngx_http_ssl_module.html), [Blocky rebinding protection](https://0xerr0r.github.io/blocky/main/configuration/), [reusable dashboard module](../../nix-homelab/modules/operations/dashboard.nix).

Read official project documentation and release pages on 2026-10-01 and inspected the local operations module. Full desktop configuration evaluation on a MacBook copy of the working tree produced 42 Gatus probes, including 24 HTTPS probes, and 24 Homepage cards: 23 HTTPS links plus the Gatus summary tile. The reviewed configuration gives every local dashboard card the approved client CIDRs; the reusable module asserts this unless a restricted card is explicitly acknowledged. All NixOS assertions passed. The desktop system built and activated with the dashboard route, login rate limit, and regenerated DNS allowlist. Sealed activation artifacts reported ready. An authenticated request using the runtime password returned Homepage with all 23 HTTPS links. TLS-verified requests to all 23 service URLs succeeded from both desktop and a second LAN host, including the two sites that returned policy 403 before activation. All 23 sent HSTS. The iPhone's existing WireGuard path to a desktop and a Pi HTTPS site was confirmed by its user; dashboard login on the iPhone has not been tested. The switch reported four initial service setup failures that recovered on retry. Alert delivery and resource measurements have not been tested. The hosted `gatus.io/docs` pages describe a managed product, so Gatus conclusions use the self-hosted `TwiN/gatus` repository. The working tree has substantial unrelated changes; this note does not attribute their provenance.

## Implication for this repository

1. Derive browser-facing Homepage cards from the declared desktop and Pi HTTPS sites. Retain the existing host-local application health probes separately.
2. Group cards by service area and deployment, with a Gatus summary tile, search, icons, and a consistent layout. The cards themselves are the service bookmarks.
3. Check the HTTPS browser routes as well as internal health URLs. Verify certificate expiry and accept documented login responses; these checks do not prove an authenticated workflow.
4. Keep the tested desktop generation active and verify dashboard login from a VPN browser. Add alert delivery only with a private runtime credential and a tested subscriber.

The shared operations module enables Gatus and Homepage together and uses a single endpoint inventory for local health checks. The reusable dashboard module now derives Homepage cards and separate HTTPS/TLS probes from declared HTTPS sites and accepts remote sites through a catalog. The desktop supplies its login credential, Pi site discovery, and optional labels and groups; SQLite history is bounded. Homepage and Gatus still listen on desktop loopback. The desktop HTTPS proxy makes Homepage available to permitted LAN and VPN clients after login; Gatus remains local, and alert delivery has no configured provider. A concurrent flake update introduced an unrelated guarded package revision mismatch after the successful fixed generation was built; that source state needs separate review before another source-based switch.
