# Stirling PDF 3 for a self-hosted homelab

Reviewed: 2026-09-28. Scope: upstream v3.0.1 release and documentation available on this date, plus the local validation described below.

## Answer

For a temporary native NixOS deployment, the versioned [v3.0.1 `Stirling-PDF-with-login.jar` release asset](https://github.com/Stirling-Tools/Stirling-PDF/releases/download/v3.0.1/Stirling-PDF-with-login.jar) can be pinned by hash in Nix. Upstream's [Unix guide](https://docs.stirlingpdf.com/Installation/Unix%20Installation/) says this JAR bundles the frontend and backend with authentication and additional features; the plain JAR omits authentication, and the `server` JAR omits the UI. The [v3.0.1 release](https://github.com/Stirling-Tools/Stirling-PDF/releases/tag/v3.0.1) is the current hotfix after v3.0.0, with a backend shutdown fix and desktop/UI changes. The login-enabled JAR contains proprietary components under [separate license terms](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/proprietary/LICENSE); review those terms before relying on this package or distributing its modified output.

Run one unprivileged native service behind the homelab's HTTPS reverse proxy, with the application port reachable only from that proxy. Give it a writable working and state directory for settings and the embedded database. Start without server-side file storage, unattended Processor sources, a global API key, or cloud account linking. These are separate capabilities with different retention, access, and network implications. The [production guide](https://docs.stirlingpdf.com/Production-Deployment-Guide/) requires HTTPS and documents forwarded host/scheme handling; the [configuration guide](https://docs.stirlingpdf.com/Configuration/) explains settings precedence.

## Findings and sources

### Nixpkgs package and license review

The Nixpkgs package at the [reviewed pin](https://github.com/NixOS/nixpkgs/blob/4975466d324710c576dc11ad614684e6bd8cad8e/pkgs/by-name/st/stirling-pdf/package.nix) is a v2.14.3 source build. Its npm, Cargo, and Gradle dependencies have independent fixed inputs, and it applies three source patches. A v3 overlay that changes only `version` and `src.hash` would still use the v2 dependency caches. A real source-build overlay must refresh those inputs, review the patches, and test the resulting frontend and service. Nixpkgs' [overrideAttrs guidance](https://nixos.org/manual/nixpkgs/unstable/#sec-pkg-overrideAttrs) supports this approach, and its [Gradle guide](https://github.com/NixOS/nixpkgs/blob/master/doc/languages-frameworks/gradle.section.md) covers refreshing the Gradle cache. Replacing every build phase with a release-JAR install would be an overlay in syntax only; it would not meaningfully reuse the Nixpkgs recipe. The existing [NixOS service module](https://github.com/NixOS/nixpkgs/blob/4975466d324710c576dc11ad614684e6bd8cad8e/nixos/modules/services/web-apps/stirling-pdf.nix) already accepts a package override, so the temporary v3 package keeps upstream service integration.

The v3.0.1 JAR directly contains `BOOT-INF/lib/proprietary-3.0.1-plain.jar`. The [root license](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/LICENSE) excludes proprietary directories from MIT, and the [proprietary license](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/proprietary/LICENSE) restricts production use, modification, and redistribution. Source building with additional features does not remove this issue. The temporary package now declares both MIT and unfree licensing, records bundled bytecode and native code, and installs the relevant license notices. Its font workaround modifies the release JAR during a local Nix build. Those terms need review before production use or distribution of that modified output. The exact effect on a particular personal homelab use is a license question beyond this packaging test.

### Release and feature boundary

The [v3.0.0 release](https://github.com/Stirling-Tools/Stirling-PDF/releases/tag/v3.0.0) introduces Processor, a revised text editor, free OAuth SSO, a files library, and UI changes. Upstream calls Processor its first major release and expects frequent fixes. The release also marks PDF/UA conversion as work in progress. The [v3.0.1 hotfix](https://github.com/Stirling-Tools/Stirling-PDF/releases/tag/v3.0.1) includes a backend shutdown fix. A rollout should test the editor's core operations and any desired Processor workflow against real sample documents before treating the new features as dependable.

The [v3.0.1 GitHub release](https://github.com/Stirling-Tools/Stirling-PDF/releases/tag/v3.0.1) supplies the three JARs as distinct assets. Fetch the versioned asset, not the mutable `files.stirlingpdf.com` URL shown by the [Unix guide](https://docs.stirlingpdf.com/Installation/Unix%20Installation/). That guide requires Java 25 or later. For document conversion and OCR it lists LibreOffice, Tesseract, OpenCV/Python helpers, pngquant, and other optional tools. It also says some OpenCV operations need the repository's `scripts` directory alongside the JAR. Package that directory from the same v3.0.1 source revision if those operations are expected to work; test them rather than assuming the JAR is self-contained for every tool. The guide's example systemd service runs as root, but an unprivileged account with explicit writable paths is a safer local choice.

The [Docker guide](https://docs.stirlingpdf.com/Installation/Docker%20Install/) remains an alternative: standard and `fat` images include login, while `ultra-lite` does not. The `fat` image adds fonts and conversion tools. A container deployment would need a versioned tag and immutable digest, not `latest`.

### Authentication and network

The with-login JAR has authentication enabled by default. Without configured initial credentials, a fresh instance creates `admin` with password `stirling` and forces a change on first login. When both initial username and password are configured, [v3.0.1 creates the account with the first-login flag cleared](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/proprietary/src/main/java/stirling/software/proprietary/security/InitialSecuritySetup.java). Set a strong initial password through protected configuration before first startup. Persist the service's working directory and database. The [security guide](https://docs.stirlingpdf.com/Configuration/Security/System%20and%20Security/) documents the initial-login settings. Keep the app's HTTP listener private to the proxy; set the external frontend URL and pass the original host and HTTPS scheme as the [production guide](https://docs.stirlingpdf.com/Production-Deployment-Guide/) describes. `robots.txt` visibility settings do not replace access control.

OIDC is free in v3. Its [configuration guide](https://docs.stirlingpdf.com/Configuration/Security/OAuth%20SSO%20Configuration/) recommends `loginMethod: all` while bootstrapping, then testing an OIDC user and promoting it to admin before switching to `oauth2` only. Generic providers need discovery; the callback URL's provider segment must match the configured provider. Set `blockRegistration` or manage account creation deliberately if the provider serves more users than this instance should admit. Leave OAuth debug logging off after diagnosis because it records identity claims. A local account remains a practical recovery path until OIDC login and admin role are verified.

Avoid a custom global API key for ordinary use. The [API guide](https://docs.stirlingpdf.com/API/) says it works independently of user authentication; user-specific API keys provide better attribution and narrower rotation. Restrict any exposed API path with the same proxy and authentication assumptions as the UI.

### Data, storage, and backups

The [configuration guide](https://docs.stirlingpdf.com/Configuration/) gives the embedded database filename pattern. The [Unix guide](https://docs.stirlingpdf.com/Installation/Unix%20Installation/) places `configs/custom_settings.yml` beneath the JAR's working directory in its example. A native service should put writable state in its state directory and set its working directory deliberately. Back up that state and test a restore before upgrades. A writable, size-bounded temporary area is needed for large processing jobs; upstream's [performance guide](https://docs.stirlingpdf.com/Configuration/Operations/Performance-Optimization/) says large PDFs spill to disk.

Server-side file storage is a separate, currently **alpha** feature. The [storage guide](https://docs.stirlingpdf.com/Configuration/Storage/File-Sharing-Storage/) requires login, recommends local filesystem storage for most installations, and supports per-file, per-user, and total quotas. It also documents `STORAGE_ENABLED=true`, `STORAGE_PROVIDER=local`, and a local base path. If enabled, mount that path persistently, add it to backup and retention policy, set quotas, and decide whether sharing should be enabled. Share links still require login and a configured frontend URL. The v3 files library can show both browser-session and server-saved items; do not infer that every file a user sees is in the server backup from that UI alone.

### Resource use and operations

Upstream's [sizing guide](https://docs.stirlingpdf.com/Configuration/Operations/Performance-Optimization/) gives 2 GB RAM as a minimum and 4 GB as a recommendation for a small team, plus 10 GB of disk. It describes PDFs up to 10 MB as memory resident, 10–50 MB as partly disk backed, and larger files as disk backed. Rendering and OCR can expand memory far beyond input size. Begin with one service instance, a bounded upload size matched at the proxy, and measured CPU, memory, and temporary disk usage. Set a JVM heap ceiling only in relation to the service memory ceiling: upstream recommends at least 1.5 times the heap limit to leave room for LibreOffice, Tesseract, and other processes. The [production guide](https://docs.stirlingpdf.com/Production-Deployment-Guide/) documents upload limits and proxy timeouts.

The [process-limits guide](https://docs.stirlingpdf.com/Configuration/Operations/Process-Limits/) already limits LibreOffice and Tesseract to one session each by default. Keep these defaults until monitoring shows a queue problem. Raising limits can multiply memory use; the guide notes some listed external tools may not be active in the current release. Disable unneeded endpoint groups only after confirming the tool names in the running v3 UI; upstream's [production guide](https://docs.stirlingpdf.com/Production-Deployment-Guide/) documents endpoint management. Health and metrics endpoints are described in the [production guide](https://docs.stirlingpdf.com/Production-Deployment-Guide/) and [usage monitoring guide](https://docs.stirlingpdf.com/Configuration/Automation/Usage%20Monitoring/); check their authentication and license behavior on the running JAR before placing a public monitor on them.

Set `SYSTEM_ENABLEANALYTICS=false` to disable the consent prompt and both PostHog and Scarf in a private homelab. Upstream's [analytics guide](https://docs.stirlingpdf.com/analytics-telemetry/) says the unset state prompts the first visitor to make a global choice. This switch concerns analytics; it should not be treated as proof that every optional integration or update check is disabled.

### Processor and UX

Processor is browser-only at this release and requires login. On self-hosted installations, administrators manage sources and pipelines. The [setup guide](https://docs.stirlingpdf.com/Processor/Setup-and-Access/) says folder access is empty by default, while Stirling's own storage and watched folders remain allowed. `policies.allowedFolderRoots` grants all signed-in users access to processing folders under those roots, so mount a dedicated directory and allow only that directory when a folder workflow is actually needed. Use separate inbox and output directories, test with a replaceable file, and initially create the pipeline paused, as in the [first-pipeline guide](https://docs.stirlingpdf.com/Processor/Getting-Started/). Keep original files during the first trials.

The [v3 release notes](https://github.com/Stirling-Tools/Stirling-PDF/releases/tag/v3.0.0), [API guide](https://docs.stirlingpdf.com/API/), and [account-linking guide](https://docs.stirlingpdf.com/Stirling%20Account%20Link/) describe a 1,000-document-unit monthly allowance for an unlinked server's automation/API work, with interactive non-AI editing outside that allowance. One unit is charged per 25 pages or 5 MB, whichever is greater, according to account linking. Upstream's [storage guide](https://docs.stirlingpdf.com/Configuration/Storage/File-Sharing-Storage/) says self-hosted storage does not use credits; that statement is about storage, not necessarily Processor or API processing. This commercial boundary is new enough to verify in the running v3 instance before designing an unattended workload around it. Account linking shares allowance and usage with Stirling Cloud; leave it unlinked for a local-first installation unless that benefit is wanted.

For a clean UI, retain the default editor tools at first, choose the household's locale, and use the v3 quick access bar and search. Limit languages or hide endpoints only to solve an observed navigation problem; hidden endpoints can surprise API users and older links. The [configuration guide](https://docs.stirlingpdf.com/Configuration/) describes locale precedence, while the [production guide](https://docs.stirlingpdf.com/Production-Deployment-Guide/) describes language and endpoint controls. Set the frontend URL only once the reverse-proxy hostname is final so login redirects and sharing links are correct.

### Local AI

Stirling PDF v3 requires its [separate AI engine](https://docs.stirlingpdf.com/AI/Self-Hosting%20the%20AI%20Engine/) for self-hosted AI. Pin the engine image by digest, run it under a dedicated rootless account, bind its HTTP listener to loopback, and share a generated secret with the native Stirling service. Configure both [language and embedding providers](https://docs.stirlingpdf.com/AI/Model%20Providers/) to local Ollama so document content stays on this host. The engine stores extracted text, embeddings, and settings in its data directory. This host mounts that directory as a 512 MB tmpfs with mode `0700`, so those records disappear when the engine stops and stay out of disk backups. Rootless Podman cannot apply `noswap` to this mount; the host's disk swap is encrypted, but tmpfs pages may use it under memory pressure. The Java service sends the engine its settings at startup; local Ollama defaults cover an engine restart before that push. AI settings and prompts can include document text and filenames, as the [AI security guide](https://docs.stirlingpdf.com/AI/AI%20Security/) explains.

The requested [Qwen 3.5 9B Q4_K_M Ollama tag](https://ollama.com/library/qwen3.5/tags) is a 6.6 GB download and advertises a 256K maximum context. A local trial began with an 8K derived Ollama model manifest. Concurrent loading checks led to a 24K setting: Qwen and the embedding model both remained entirely on the GPU, while a larger trial offloaded part of the embedding model. The derived manifest does not copy the model weights. Set one inference request at a time, allow the small local embedding model alongside Qwen, and let Ollama unload idle models after one minute. The pre-existing Ollama service also serves another application; the shorter idle time applies to it too. Model files remain on disk and Ollama itself keeps running.

#### Qwen context sizing

Reviewed 2026-09-28. [Qwen's 9B model card](https://huggingface.co/Qwen/Qwen3.5-9B) gives a native limit of 262,144 tokens. That is a model capability, not a deployment target. [Ollama's context guide](https://docs.ollama.com/context-length) says larger allocations use more VRAM and recommends checking `ollama ps` for the allocated context and whether inference stays entirely on the GPU. A derived [Modelfile](https://docs.ollama.com/modelfile) can set `PARAMETER num_ctx` for Stirling's model without changing the default context of other Ollama clients. Choose the largest measured allocation that leaves room for the desktop workload and the embedding model, then test a representative document question; a short prompt alone checks loading, not useful long-context behavior.

[Ollama's FAQ](https://docs.ollama.com/faq) says parallel requests multiply context memory, and its default `OLLAMA_NUM_PARALLEL` is one. Flash Attention activates automatically on supported backends. The default K/V cache uses `f16`; `q8_0` uses roughly half as much cache memory with a possible precision cost, while `q4_0` trades more precision for further savings. Cache quantization requires Flash Attention and is a **global** Ollama setting, so testing it must include other local clients. Keep `f16` when the desired context fits with sufficient headroom. Keep the short idle unload through `OLLAMA_KEEP_ALIVE`, which Ollama documents as a server default that individual API requests may override.

Stirling does not pass every page of a PDF in one prompt. Its [v3.0.1 engine defaults](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/engine/.env) set retrieval chunks to 512 **characters**, as confirmed by the [chunker source](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/engine/src/stirling/documents/chunker.py). The engine also uses 16,000-character slices for long-document reasoning and folds long notes. Its [AI settings reference](https://docs.stirlingpdf.com/AI/AI%20Settings%20Reference/) defines Smart and Fast max tokens as **output** caps, while `topK` limits retrieved chunks per search. A larger model context can retain more retrieved text, instructions, and conversation history during a call, but it does not make the engine place an entire long PDF in one request. Reserve space for the output cap when testing realistic prompts.

The [v3.0.1 settings card](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/frontend/editor/src/proprietary/components/shared/config/configSections/ai/AiModelsCard.tsx) shows its 16K Ollama context advice whenever the provider base URL field is visible. It does not inspect the loaded model. A live request to the 24K derived alias with no per-request context override processed 21,651 synthetic prompt tokens and recalled markers from both ends; Ollama reported a 24,576-token allocation with the full model on the GPU. The advice remains visible because it is static UI text.

Qwen's default thinking output can exhaust a structured response's token budget before returning an answer. For the engine's OpenAI-compatible chat requests, a loopback-only adapter sets `reasoning_effort: none`, which [Ollama maps to disabled thinking](https://github.com/ollama/ollama/blob/main/openai/openai.go). Embedding requests go directly to Ollama. A live non-streaming JSON-schema request returned content without a reasoning field, and both non-streaming and streaming requests through the adapter returned answers. This adapter is specific to the local Ollama chat endpoint; revisit it if Stirling's engine gains a native reasoning setting.

### Redacting sensitive documents

Reviewed against the v3.0.1 source on 2026-09-28. The [redaction guide](https://docs.stirlingpdf.com/Functionality/Page-Operations/redact/) describes automatic text removal and says PDF-to-image conversion is on by default. The [v3.0.1 editor defaults](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/frontend/editor/src/core/hooks/tools/redact/useRedactParameters.ts) and [API request defaults](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/core/src/main/java/stirling/software/SPDF/model/api/security/RedactPdfRequest.java) set `convertPDFToImage` to **false**. There is no server-wide redaction default in the v3.0.1 application settings. For sensitive exports, explicitly enable **Convert PDF to PDF-Image** before automatic redaction. This [renders visible pages into a new image-only PDF](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/common/src/main/java/stirling/software/common/util/PdfUtils.java), so the source's selectable text, hidden text, annotations, and embedded file objects are not carried into the output. The image-only PDF has no searchable text. Run [Stirling's OCR tool](https://docs.stirlingpdf.com/Functionality/OCR/) on that export to add a new selectable layer from the visible, non-redacted words. OCR can misread words and does not restore the original PDF's tagged structure or vector text. Keep the original in protected storage if its fidelity is needed.

Do not treat a black rectangle as proof of removal. The [automatic controller](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/core/src/main/java/stirling/software/SPDF/controller/api/security/RedactController.java) can fall back on native redaction failure to a [service that only draws rectangles](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/core/src/main/java/stirling/software/SPDF/controller/api/security/ManualRedactionService.java). With image conversion off, that fallback can leave the original text extractable, though successful native removal preserves searchable text outside the redacted area. The same service powers the manual REST endpoint and covers areas and pages without deleting underlying objects. The current editor handles [manual marks in its browser viewer](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/frontend/editor/src/core/hooks/tools/redact/useRedactOperation.ts), so the REST behavior does not establish the editor's manual behavior. For manual edits, apply the marks, export the result, then use [PDF-to-image and image-to-PDF conversion](https://docs.stirlingpdf.com/Functionality/Convert/) to build a fresh PDF from the visible pages before OCR. Never choose the `OVERLAY_ONLY` API strategy for sensitive redactions; the [execute service](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/core/src/main/java/stirling/software/SPDF/controller/api/security/RedactExecuteService.java) expressly skips text removal in that mode. Automatic matching may miss text in scans, drawings, unusual encodings, or text it cannot identify. Inspect every resulting page and try selecting, copying, and searching for each secret in the **final OCR export**. Use a replaceable synthetic fixture to test the workflow before processing real documents.

Redaction alone is not a complete metadata scrub. The [Sanitize endpoint](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/core/src/main/java/stirling/software/SPDF/controller/api/security/SanitizeController.java) offers separate removal switches for document information, XMP metadata, attachments, JavaScript, links, and fonts. Apply the relevant switches to the final export and inspect its metadata and attachments before release. Avoid sending the unredacted original to AI chat unless the task requires it: [language models receive prompts, relevant text, conversation history, and filenames; embedding models receive document text and search queries](https://docs.stirlingpdf.com/AI/AI%20Security/). The models and engine run locally, and the engine's document index is temporary, but a chat still processes the original text.

The browser is another copy of the source. Stirling's [browser storage description](https://docs.stirlingpdf.com/Functionality/The%20Technologies/) says files persist in IndexedDB between operations; its [version-history guide](https://docs.stirlingpdf.com/Migration/New-Features/) says prior versions are retained locally. Delete the original, redacted working copies, and history from the Stirling workspace when finished, and clear site storage or use a dedicated browser profile on shared machines. Server-side temporary files are managed and periodically cleaned, but [v3.0.1 defaults to a 24-hour maximum age and a 30-minute cleanup interval](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/common/src/main/java/stirling/software/common/model/ApplicationProperties.java). This host shortens those to two hours and 15 minutes and keeps temporary files in the service's private `/tmp`, outside backups. Successful cleanup is not secure erasure of underlying media. The [shutdown hook](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/common/src/main/java/stirling/software/common/config/TempFileShutdownHook.java) only handles files still registered in that process. The private HTTPS proxy streams uploads and does not buffer PDF responses to disk; it sends `Cache-Control: no-store`, a no-referrer policy, and a browser `connect-src` restriction for the PDF site. These headers do not clear IndexedDB.

Logs need special care. The [automatic redaction controller](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/core/src/main/java/stirling/software/SPDF/controller/api/security/RedactController.java) logs search terms at DEBUG and the original-derived filename at INFO. The [unified execute service](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/app/core/src/main/java/stirling/software/SPDF/controller/api/security/RedactExecuteService.java) logs text-range delimiters at INFO and an unmatched delimiter at WARN. This host disables that redaction controller package's logs, suppresses proxy access logging, and disables AI engine access logging. Avoid descriptive filenames and restrict journal access because other exceptions may still include input details. The [analytics switch](https://docs.stirlingpdf.com/analytics-telemetry/) disables PostHog and Scarf, but it does not disable configured AI, cloud links, external integrations, or local logging. This host also disables account linking and cloud document indexing and limits the PDF server, AI engine, and Ollama runtime to loopback network connections. The AI engine's image and Ollama models are fetched by separate services before those runtime network restrictions apply.

## Validation and limits

The v3.0.1 login-enabled JAR was fetched and pinned as `sha256-pPm6InqYudIPQw972Dyk/NIjV1VLiNx+UjjUDHqTjBM=`. Its package smoke test started the JAR with login enabled, confirmed the generated admin credential replaced the default, and received `{"version":"3.0.1","status":"UP"}`. The desktop system build, package evaluation, and generated-unit check passed. After activation on the desktop, Stirling and the AI engine both passed their health checks. The private HTTPS site returned `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; the engine rejected an unauthenticated request. The engine data path was verified as a mode `0700` tmpfs. A synthetic document was indexed, answered using the initial 8K Qwen model, and deleted. A later concurrent-loading trial selected 24K because it kept both local models entirely on the GPU. After activating the 24K configuration, Stirling reported healthy, the engine identified the new Smart and Fast model name, and a live Ollama request confirmed the allocated 24K context and full GPU residency. A synthetic document was then indexed through the engine, answered correctly at 24K, and deleted. Ollama unloaded the idle model after one minute. Browser login and automatic text redaction were subsequently exercised with synthetic PDFs; backup restore remains untested. Upstream documentation can change independently of the v3.0.1 tag. The Unix guide's service example still invokes the plain no-login JAR, although it recommends the with-login JAR in the preceding section.

The v3.0.1 editor uses EmbedPDF 2.15.0 for document viewing. Its [fallback manager](https://github.com/embedpdf/embed-pdf-viewer/blob/v2.15.0/packages/engines/src/lib/pdfium/font-fallback.ts) receives a requested face name but chooses fonts by charset, weight, and italic style, while [Stirling maps Latin fallback to Noto Sans](https://github.com/Stirling-Tools/Stirling-PDF/blob/v3.0.1/frontend/editor/src/core/services/pdfiumFontFallback.ts). A synthetic PDF using unembedded Times, Courier, and Helvetica rendered all three in a similar sans face in the browser. The pinned package now selects locally served Liberation Serif, Mono, or Sans for recognizable Latin face names, with Sans checked before the generic `serif` substring. A browser test against the previously activated package showed distinct faces; the later matching-order correction passed a package runtime test but has not had a second browser comparison. Custom unembedded faces and exact glyph spacing can still differ from a viewer with the original font installed. The package rewrite checks the original asset hash and fails on an upstream change. It changes viewer rendering only, not uploaded PDF bytes or server redaction.

## Implication for this repository

The host configuration pins the official v3.0.1 with-login JAR and matching Python helper scripts, uses Java 25 and a dynamic service user, keeps its port behind the existing private HTTPS proxy, seals the initial admin password with Nix S-E-A-L, inventories the Java application state for backup, and disables analytics. The protected runtime template supplies the bootstrap password to systemd. Stirling uses this value only when it creates the account; changing the sealed value later does not rotate an existing account password. The setup has a 100 MB upload limit and a 3 GB service memory ceiling with a 1.5 GB Java heap. The existing NixOS module supplies the external conversion and OCR tools. The local AI stack uses a digest-pinned engine and Ollama models as described above. Check a PDF operation and redaction in the browser with a synthetic document before using sensitive originals. Server file storage, Processor folder access, and OIDC remain separate choices.
