# Deploying nix-darwin from Linux with deploy-rs

Reviewed: 2026-10-05. Scope: deploy-rs revision `e760371d631165e7d8de5b0dcf148e21ec4c16f0` and nix-darwin configuration in this repository. The question is whether a separate root SSH command is required and how to deploy a Mac system without a sudo prompt.

## Answer

A separate `ssh root@<HOSTNAME>` command is **not required**. It is an optional, narrow diagnostic for key authentication and reachability. deploy-rs itself opens SSH connections to copy or remotely build the closure, run activation, and confirm connectivity. The normal command can be the first test of root SSH. This follows from the deploy-rs [remote build code](https://github.com/serokell/deploy-rs/blob/e760371d631165e7d8de5b0dcf148e21ec4c16f0/src/push.rs), [activation code](https://github.com/serokell/deploy-rs/blob/e760371d631165e7d8de5b0dcf148e21ec4c16f0/src/deploy.rs), and [rollback description](https://github.com/serokell/deploy-rs/blob/e760371d631165e7d8de5b0dcf148e21ec4c16f0/README.md).

## Findings and sources

- deploy-rs distinguishes `sshUser`, the login identity, from `user`, the profile owner. It invokes sudo only when those values differ. Setting both to `root` uses root key authentication without a sudo step. A non-root SSH account with passwordless sudo is the upstream Darwin example's alternative; the example's statement that password provisioning is unsupported conflicts with this revision's `interactiveSudo` option, so use the pinned [README settings](https://github.com/serokell/deploy-rs/blob/e760371d631165e7d8de5b0dcf148e21ec4c16f0/README.md) and [identity selection code](https://github.com/serokell/deploy-rs/blob/e760371d631165e7d8de5b0dcf148e21ec4c16f0/src/lib.rs) for this version.
- The [Darwin activation helper](https://github.com/serokell/deploy-rs/blob/e760371d631165e7d8de5b0dcf148e21ec4c16f0/flake.nix) wraps the nix-darwin system toplevel and invokes `$PROFILE/activate` with `HOME=/var/root`. Use `deploy-rs.lib.aarch64-darwin.activate.darwin` for an Apple Silicon target; the helper's platform follows the target system.
- `remoteBuild = true` builds on the target and fetches its external dependencies there. The [upstream Darwin example](https://github.com/serokell/deploy-rs/blob/e760371d631165e7d8de5b0dcf148e21ec4c16f0/examples/darwin/flake.nix) explicitly recommends it when the deployer is not Darwin; the [implementation](https://github.com/serokell/deploy-rs/blob/e760371d631165e7d8de5b0dcf148e21ec4c16f0/src/push.rs) copies the derivation to an `ssh-ng` store before building remotely.
- `autoRollback` and `magicRollback` default to true. The latter waits for a file removal event after activation. On this Mac, activation succeeded and the deployment client removed the canary, but the [Darwin watcher](https://github.com/serokell/deploy-rs/blob/e760371d631165e7d8de5b0dcf148e21ec4c16f0/src/bin/activate.rs) did not observe that event before its timeout. This node disables `magicRollback`; `autoRollback` remains enabled for activation errors. A successful deployment therefore does not gain a timed connectivity rollback.
- The Mac must first allow the selected account to use Remote Login. [Apple's Remote Login guide](https://support.apple.com/guide/mac-help/allow-a-remote-computer-to-access-your-mac-mchlp1066/mac) documents enabling SSH and choosing allowed users. Therefore a one-time local activation is necessary if root's SSH authorization exists only in an unapplied nix-darwin generation. After that, the separate SSH command adds no required setup step.
- A [nix-darwin issue report](https://github.com/nix-darwin/nix-darwin/issues/1758) describes remote root or sudo activation failing when it tries to reload a primary user's LaunchAgent outside that user's GUI launchd domain. The [pinned nix-darwin source](https://github.com/nix-darwin/nix-darwin/blob/4cff07de74b50e64bdd68cd4e722ab5b6b35ee48/modules/system/launchd.nix#L34-L49) still runs `launchctl asuser ... launchctl load -w` without handling that failure. A [proposed upstream fix](https://github.com/nix-darwin/nix-darwin/pull/1759) checks whether the user's GUI domain is reachable before loading; the pull request remained open when reviewed. This is a reported failure and proposed fix, not a failure observed on this Mac.
- The pinned [Home Manager app-copy activation](https://github.com/nix-community/home-manager/blob/4b9add8645d5e2b0f7de18f7a442d08fe2bdcc91/modules/targets/darwin/copyapps.nix) checks whether apps may be updated over SSH and stops when remote users lack Full Disk Access. [Apple's Remote Login guide](https://support.apple.com/guide/mac-help/allow-a-remote-computer-to-access-your-mac-mchlp1066/mac) identifies the GUI setting. This is a macOS permission prerequisite for the selected copied-app profile, separate from SSH key authentication.

## Validation and limits

Reviewed the pinned deploy-rs README, Darwin example, and source, plus this repository's [deployment node](../../hosts/shared/local/flake/deploy.nix), [Mac SSH module](../../hosts/darwin/macbook-pro-m4/local/ssh.nix), and selected host modules. A static search found no `launchd.user.agents`, `launchd.user.envVariables`, or `environment.userLaunchAgents` declaration in the selected system modules. Home Manager declares agents through a separate activation path. A desktop-initiated Darwin system build completed on the Mac; the first activatable wrapper failed its Darwin watcher tests, then built with this repository's guarded Darwin package fix. Home Manager activation succeeded after Full Disk Access was enabled for remote users. After the root SSH policy was activated, the desktop completed `just macbook-deploy` with no sudo prompt. The Mac's active system and system profile point to the deployed generation. The deploy-rs timeout behavior above was observed during this validation, so the successful deployment used `magicRollback = false`.

## Implication for this repository

The deployment node sets root for both identities, enables target-side building, and uses the native Darwin helper with the guarded Darwin deploy-rs package. Once the Mac grants Full Disk Access to remote users and admits the root key, run `just macbook-deploy` from the desktop. `just macbook-build` is an optional dry activation preview. A standalone `ssh` command is useful only to isolate an authentication failure if deployment cannot connect.
